Cheat sheet · requests & limits
The syntax, and what to set it to by workload
Pod spec · resources block, by QoS class
Guaranteed 
resources:
  requests:
    cpu: "1"
    memory: "512Mi"
  limits:
    cpu: "1"
    memory: "512Mi"
Both resources, request == limit. Last evicted — but every burst is capped at steady state.
Burstable 
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    memory: "512Mi"
    # cpu limit removed
    # — no CFS quota,
    # no self-throttling
Memory capped, CPU uncapped. Protected floor via cpu.shares, but free to burst into idle node CPU.
BestEffort 
resources: {}


# nothing set —
# nothing to
# bin-pack or
# protect
Nothing set, nothing reserved. Free to schedule anywhere — first evicted under any pressure.
Best practice, by workload
Workload Memory: request = limit? CPU limit? Because
Latency-sensitive API
Guaranteed		 Yes — size from p99 + headroom Omit, or set well above p99 A capped limit throttles the first burst above steady state
Database / cache / stateful
Guaranteed		 Yes — mid-request OOM = corrupt state Omit — bursts are normal, not a bug Eviction priority matters more than bin-packing efficiency
General app / spiky CPU
Burstable		 Set a limit — cap the leak risk Omit — let it burst into free node CPU cpu.shares still protects it under contention; a ceiling only costs idle cycles
Batch / cron / reconciliation
Burstable		 Set a limit above expected peak OK to cap — no one's waiting on it Throttling a batch job is fine; an unbounded one isn't
Dev / non-critical
BestEffort		 Optional Optional First to be evicted is the point — nothing depends on it
