Just add a retry.

It's one of the most dangerous sentences in payments engineering — and almost nobody says it maliciously. It just sounds harmless.

Here's why it isn't.

In most systems, a timeout means “that failed, try again.” In payments, a timeout means something narrower and much more dangerous: “I don't know what happened.” Those are two different problems, and treating them the same is where the damage happens.

Walk through the trace (image below):

A client sends a debit request for $500. The payment gateway forwards it to the core ledger. The ledger processes it, posts the debit, and sends back a 200 OK.

That response never makes it back to the client. Network blip, load balancer hiccup, doesn't matter — the request succeeded, but the confirmation didn't survive the trip home.

The client sees nothing. No error, no confirmation — just silence. So it does the “safe” thing: it retries. Same request. Same amount. No idempotency key to say “you've seen this before.”

The gateway has no way to know this is a repeat. It forwards the request again. The ledger — doing exactly what it's designed to do — posts a second, perfectly valid debit.

End state: two successful transactions, $1,000 debited for a $500 purchase, and not a single exception thrown anywhere in the stack. No alert fires, because nothing here looks like a failure. It looks like two customers making two payments.

That's what makes this bug class so dangerous — it doesn't crash. It just quietly moves money.

The fix isn't “don't retry.” Distributed systems fail constantly; retries are necessary for recovery. The fix is refusing to let a retry be a blind repeat of an ambiguous request:
→

Treat “no response” as unknown, never as failed.

→

The caller generates the idempotency key — not the server. Whatever initiates the request (the mobile app, the web client, or the upstream service on a server-to-server call) creates a unique key, usually a UUID, at the exact moment the action is triggered — the “pay now” tap, not the HTTP call. That same key rides along on every retry of that same logical request. The server's job is simple: look the key up first. Seen it before? Return the original result. Never seen it? Process it, and store the result against that key.

→

Make the ledger the single source of truth. Before retrying, ask it what already happened — don't just resend and hope.

The hard part was never the retry logic. It's the idempotency guarantee underneath it — and in my experience, that guarantee rarely gets built proactively. It gets built the week after the first customer complaint about being charged twice.
